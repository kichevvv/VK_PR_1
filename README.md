# **Отчёт по практической №1**

# **1\. Вариант и масштаб**

| Поле | Значение |
| :---- | :---- |
| ФИО (как в VK Education) | Иванищев Кирилл Александрович |
| Вариант (запрос) | Q18 «Large Volume Customer» |
| Масштаб sfN | sf1 |
| Почему выбрал такой масштаб | Выбранный масштаб sf1 обеспечивает достаточный объем данных (около 6 млн строк в таблице `lineitem`), чтобы наглядно продемонстрировать разницу в эффективности кодеков сжатия. При этом размер датасета позволяет комфортно выполнять вычисления на локальном компьютере, в отличие от масштаба sf10. Масштаб sf0.01 слишком мал для оценки производительности. |

# **2\. Поднятые сервисы — и почему именно они**

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO (Silo) | S3-хранилище (сюда сохраняются parquet-файлы) | Использован образ Silo, так как он предоставляет необходимый S3-совместимый API и удобен для локального развертывания в текущих условиях. Обычный локальный диск не позволяет эмулировать работу Lakehouse. |
| PostgreSQL | БД для метаданных Lakekeeper | Надежная и нетребовательная к ресурсам реляционная база данных. Оптимально подходит для хранения метаданных каталога. |
| Lakekeeper | Iceberg REST Catalog | Открытый каталог, который легко интегрируется с Trino через стандартный REST API. |
| Trino | SQL-движок | Выполняет чтение и запись данных. Обладает хорошей производительностью и поддерживает встроенную генерацию данных через TPC-H коннектор. |
| Metabase | отчёт/дашборд поверх Gold | Выбран благодаря низким системным требованиям: устанавливается одним контейнером со Starburst драйвером. Является легковесной альтернативой Superset. |

**Скрипты, которыми поднимал стек:**

```sh
# 1. Запуск базовой инфраструктуры (S3, PostgreSQL, Lakekeeper, Trino)
# docker compose up -d

# 2. Скрипт ожидания готовности SQL-эндпоинта Trino к работе
# ./scripts/wait_trino.sh

# 3. Запуск полного цикла ELT (создание слоев Bronze - Silver - Gold)
# ./scripts/pipeline.sh

# 4. Запуск тестов производительности (бенчмарк кодеков GZIP и ZSTD)
# ./scripts/benchmark.sh

# 5. Запуск BI-инструмента Metabase (вынесен в отдельный профиль)
# docker compose --profile bi up -d
```

# **3\. Разбор запроса — какие данные нужны**

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает |
| :---- | :---- | :---- |
| customer | `custkey`, `name` | Соединение с таблицей заказов. Поле `name` используется в финальной выборке. |
| orders | `orderkey`, `custkey`, `orderdate`, `totalprice` | Соединение с клиентами и позициями заказа. Фильтрация данных. Поле `totalprice` используется для сортировки и вывода. |
| lineitem | `orderkey`, `quantity` | Подзапрос: группировка по заказам, где суммарное количество товаров превышает 300\. |

# **5\. Тесты производительности**

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Вывод |
| :---- | :---- | :---- | :---- |
| GZIP | \~7.9 с | 182.5 МБ | Базовый алгоритм. Показывает средние результаты степени сжатия и скорости чтения. |
| ZSTD | \~4.2 с | 165.3 МБ | Кодек ZSTD оказался более эффективным: он обеспечил меньший размер файлов (165.3 МБ против 182.5 МБ) и почти в два раза ускорил выполнение SQL-запроса. Является предпочтительным выбором. |

# **6\. Часть 2 — осмысление и работа с инструментами**

| Вопрос | Ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse? | Lakehouse позволяет хранить большие объемы полуструктурированных данных в объектном S3-хранилище, предоставляя при этом SQL-интерфейс. Это решает проблемы масштабируемости и стоимости классических реляционных баз данных. |
| Пример schema evolution на Silver | При добавлении новой колонки старые файлы parquet не перезаписываются. Iceberg создает новый файл метаданных, что позволяет применять изменения схемы без полного перестроения таблицы. |
| Пример скрипта time travel | Time travel позволяет обращаться к предыдущим состояниям таблицы или отменять изменения. Команда `CALL iceberg.system.rollback_to_snapshot('silver', 'q18_joined', ID_СНАПШОТА);` восстанавливает данные на момент указанного снимка. |

## **6.2. Подключить инструмент к lakehouse**

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Metabase | Легкий в развертывании и настройке BI-инструмент. Подключение к Trino осуществляется быстро (указанием хоста `trino`, порта `8080` и каталога `iceberg`), что позволяет напрямую визуализировать данные слоев с помощью SQL-запросов. |

# **7\. Выводы**

В ходе практической работы успешно реализована архитектура Lakehouse. Данные логически разделены: Bronze сохраняет исходную структуру, Silver выполняет фильтрацию (заказы \> 300 товаров) и объединение таблиц, а Gold предоставляет агрегированную витрину для BI-системы. Тестирование форматов показало явное преимущество ZSTD над GZIP по скорости выполнения запросов и степени сжатия. Использование связки S3, Iceberg и Trino на практике продемонстрировало, как можно эффективно работать с файлами в объектном хранилище, используя привычный SQL-интерфейс.
